## M1 · Engine — done

Built in `crates/engine` (no Tauri): model, state machine, settings, SQLite store with FTS5
history search, toolchain manager, argv builder, output parser, error classifier, process
runner (Job Objects on Windows), probe cache with exact preset resolution, and the engine
actor with the queue scheduler. `crates/fake-ytdlp` replays recorded sessions and records new
ones (`scripts/capture-fixture.sh`).

Verified:

| What | How |
|---|---|
| Real download with live progress | `cargo run -p engine --example dl -- https://www.youtube.com/watch?v=SkVqJ1SGeL0 --preset mp4-480`: 2 streams, merge, metadata, 9.3 MB file. Also `--preset m4a` (2.5 MB, no re-encode). |
| Offline end to end with the real tools | `tests/real_tools.rs`: a local HTTP server, yt-dlp's generic extractor, ffmpeg; skipped when yt-dlp or ffmpeg is not on PATH |
| argv builder | golden tests for the default and an everything-on request, every preset, explicit format picks, bad setting values dropped, URL always after `--` |
| Parser and progress | real progress lines, nulls, NaN/Infinity, fragments, byte-weighted and stage-i-of-n progress, never backwards |
| Error classifier | 28 fixtures: 19 captured from yt-dlp on this PC, 9 messages taken from yt-dlp's source where they cannot be produced on demand (bot check, geo block, members-only, live not started, rate limit, disk full) and marked as such |
| State machine | full 8×8 transition table |
| Store | order survives reopening, FTS5 prefix search over title/uploader/site/URL, diacritics folded, missing files detected, corrupt and newer databases handled |
| Engine (18 tests with fake-ytdlp) | download to file and history; stages video→audio→merge; 5 links at concurrency 2 (peak exactly 2); per-site limit; pause keeps `.part` and resume reruns the identical argv; cancel kills a hung process and deletes its files; crash; 7 error classes; one re-probe on a 403 with cached info; quit and relaunch resumes; queue order survives relaunch; exact preset resolution without a second probe; playlist with archive marking, own folder, index prefixes, one notification; video-or-playlist question; deep links never start downloads; missing tools; Copy Details is redacted |
| Tool installs (6 tests, local HTTP server) | SHA-256 checked from `SHA2-256SUMS` or GitHub's digest, atomic switch, previous kept, rollback, unhealthy binary refused, zip entries that escape the folder skipped, no checksum means no install |
| Lint | `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings` clean |

Not verified, and why:

- Managed installs from the real GitHub (only against the local server so far). Exercised in
  M5 with the onboarding flow.
- Cookies from a browser: no supported browser on this PC has a cookie database (yt-dlp says

## M6 · Motion and polish — done

Built in this milestone: motion tuned against recorded contact sheets
(`scripts/record-motion.mjs`, `docs/screenshots/motion/`; final values and the as-built
choreography are in DESIGN.md), contrast-theme support (`forced-colors`, with its own
screenshots), drag-out of finished files, custom-drawn radios in the Formats sheet, sheets
anchored under the toolbar, every UI string moved to `ui/src/strings.ts`, and seven
interaction tests (`ui/e2e/interactions.spec.ts`: drag to reorder, Ctrl+V then Enter, a
non-link, arrow keys and Delete, Escape returns focus, the format pop-up, shift-click ranges).

Performance, release build (`scripts/measure.ps1`), Windows 11, 16 cores, WebView2 157:

| What | Result |
|---|---|
| Cold start to a visible, painted window | 614 ms first launch, then 357 and 342 ms |
| Idle CPU, window open, 30 s | 47 ms of CPU time across all 7 processes (≈0.01 % of the machine) |
| Idle memory | 380 MB working set, 176 MB private (lovelyDL plus its 6 WebView2 processes) |
| Three active downloads, 20 s | App 0.54 % CPU, 434 MB working set, 208 MB private |
| yt-dlp per download | ≈75 MB (PyInstaller launcher plus Python); its CPU stayed under Windows' 15.6 ms accounting tick at 300 KB/s per download |

The WebView2 processes account for most of the memory; lovelyDL.exe itself uses 40 MB working
set, 14 MB private.

Accessibility, checked on the real app through the UI Automation tree that Narrator reads
(Narrator itself was not run): traffic lights, toolbar buttons, the link field (with its
placeholder as help text), the sidebar tabs with counts, the Downloads grid, and each row
named "title, status". Fixed from that pass, and confirmed on a rebuilt release app: a
failed row's name was yt-dlp's raw message (hundreds of characters) instead of the short
explanation, and the sidebar's tab list had no name. Icon buttons also expose their tooltip
as help text (Chromium does this for every `title`), which Narrator may repeat at high
verbosity; kept, as tooltips are the Windows convention. Automated: axe on every mock screen
in light, dark and contrast (55 Playwright tests).

All checks: `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` (84 tests), tsc,
ESLint, Prettier, Vitest (14), Playwright (55).

Not verified, and why:

- **Keep awake while downloading**: `powercfg /requests` needs an administrator prompt. The
  code holds `SetThreadExecutionState(ES_SYSTEM_REQUIRED)` on its own thread while anything
  is active.
- **Dropping a dragged-out file** into Explorer or another app: needs real pointer input
  outside the window. Starting the drag is a native call with the finished file's path.
- **Narrator speech itself**: the tree it reads was checked instead.
- **Acrylic sidebar**: Windows "Transparency effects" is off on this PC, and turning it on is
  a system setting change.
