# lovelyDL plan

lovelyDL is a Windows app that saves video and audio with yt-dlp, with an interface modelled
on macOS: quiet, dense and smooth. This file holds the architecture, the IPC contract and the
milestone plan. Decisions and their reasons are in [DECISIONS.md](DECISIONS.md); what is done
and verified is in [PROGRESS.md](PROGRESS.md); the look and motion are in [DESIGN.md](DESIGN.md).

The original brief described a macOS app. The owner redirected it to Windows on 2026-11-17
(see DECISIONS.md). The product scope is unchanged; the platform layer was swapped.

## Architecture

```
ui/  (React 19, TypeScript, Vite)          a projection of Rust state
  │  typed commands and one typed event (generated by tauri-specta)
src-tauri/  (Tauri 2.12 shell, WebView2)   thin commands, window, tray, taskbar, protocols
  │  src/platform/                         everything OS-specific (Windows today)
crates/engine/  (pure Rust, no Tauri)      toolchain, yt-dlp driver, queue, store, settings
crates/fake-ytdlp/                         test double that replays recorded yt-dlp output
```

Rules that hold everywhere:

- Rust owns all state. The UI calls `get_snapshot` on load, then applies `Update` events. A
  reloaded web view rebuilds itself completely from the snapshot.
- The engine is one actor task. Every state change, including job state transitions, goes
  through it, so there are no shared locks and tests are deterministic.
- Commands are thin wrappers around engine calls.
- Progress is coalesced in Rust: yt-dlp emits at most 4 lines a second per stream
  (`--progress-delta 0.25`), and the engine flushes all pending changes as one event at most
  every 100 ms. Nothing ticks while nothing changes.
- yt-dlp is spawned with an argv array, never a shell, with `--` before the URL, and with
  `CREATE_NO_WINDOW` so no console flashes.

### Engine modules

| Module | Job |
|---|---|
| `model` | Every type that crosses IPC: `Job`, `Preview`, `Settings`, `Components`, `Change` |
| `state` | The one place that says which job state transitions are legal |
| `settings` | Versioned JSON file, atomic writes, defaults, migration |
| `store` | SQLite (rusqlite, bundled) on its own thread: jobs, FTS5 history search, migrations |
| `toolchain` | Find, install, verify, update and health-check yt-dlp, ffmpeg/ffprobe and Deno |
| `ytdlp::args` | Pure argv builder, covered by golden tests |
| `ytdlp::parse` | Sentinel-line parser for progress, post-processing and final path |
| `ytdlp::probe` | `-j --flat-playlist --lazy-playlist` probe, info-JSON cache, exact preset resolution |
| `ytdlp::errors` | Classifier built from captured yt-dlp output |
| `ytdlp::run` | Spawn in a Job Object, read both pipes, cancel and pause |
| `engine` | The actor: scheduler, jobs, previews, settings and components; emits `Change`s |
| `redact` | Removes cookies, auth headers and tokens from anything logged or copied |

### Job model

`Job { id, url, source, title, uploader, duration, site, thumbnail, kind, request, state,
progress, planned, output, error, attempts, group, cleared, created_at, started_at,
finished_at }`. The per-job log tail stays in Rust and is fetched on demand for Copy Details.

States: `Queued → Probing → Downloading ⇄ PostProcessing → Completed`, plus `Paused`,
`Failed { kind, retryable }` and `Canceled`. Legal transitions live in `state.rs` and are
tested as a table. `Downloading ⇄ PostProcessing` is two-way because yt-dlp runs some
post-processors (thumbnail conversion) before the download.

One table holds every job. History is the set of finished jobs; "Clear Completed" sets
`cleared` so a job leaves the Downloads list but stays in History. Playlist items are ordinary
jobs that share a `group`, so they get per-item progress, pause and retry.

### yt-dlp contract (verified against 2026.10.26, see DECISIONS.md)

Always: `--ignore-config --color never --newline --no-playlist --js-runtimes deno:<abs>
--ffmpeg-location <dir> -P home:<dest> -P temp:<job temp dir> -o <template>
--progress --progress-delta 0.25` plus

```
--progress-template download:@@lovelydl@@DL {"fid":%(info.format_id)j,"vcodec":%(info.vcodec)j,"acodec":%(info.acodec)j,"p":%(progress)j}
--progress-template postprocess:@@lovelydl@@PP %(progress)j
--print after_move:@@lovelydl@@FILE %(filepath)j
```

- Download progress and the final path arrive on stdout; post-processing lines arrive on
  stderr. Both pipes are parsed. Only sentinel lines are parsed; the rest is log text.
- `--print` implies `--quiet`, so `--progress` is always passed with it.
- Presets: Best = no alias; Compatible MP4 = `-t mp4`; a height cap = `-S res:<h>` placed
  **after** the alias (a later `-S` is prepended to the sort, so it wins); audio =
  `-t mp3`, or `-x --audio-format m4a|opus|flac` with `-S acodec:<codec>` to avoid re-encoding.
- Each job has its own temp directory on the destination's volume, so the final move is a
  rename, cancel cleanup is one directory removal, and partial files survive pause, quit and
  relaunch.
- Probe results are cached for 30 minutes as info JSON in the cache folder. Downloads inside
  that window use `--load-info-json`. Exact preset resolution runs
  `--load-info-json … --simulate --print …`, which makes no network calls.
- Pause and cancel terminate the job's Job Object (yt-dlp and any ffmpeg child). Windows has
  no SIGTERM; yt-dlp resumes `.part` files after a hard stop.

## IPC contract

Types are generated from Rust into `ui/src/ipc/bindings.ts` by tauri-specta. Nothing in that
file is written by hand. The UI imports only `ui/src/ipc/index.ts`, which picks the real
bindings inside Tauri and a scripted mock in a browser.

Commands (a failure rejects the promise with a plain message):

| Area | Commands |
|---|---|
| State | `get_snapshot` |
| Links | `add_links(text, source)`, `preview_update(id, request)`, `preview_choose(id, choice)`, `preview_dismiss(id)`, `preview_start(id, request, selection)` |
| Queue | `job_pause`, `job_resume`, `job_cancel`, `job_retry`, `job_remove`, `job_apply_fix`, `jobs_reorder`, `pause_all`, `resume_all`, `retry_failed`, `clear_completed` |
| History | `history_query(query, filter, offset, limit)`, `history_remove`, `history_trash`, `download_again` |
| Files | `reveal`, `open_file`, `copy_link`, `job_details` |
| Settings | `settings_set`, `choose_folder`, `check_folder`, `template_preview` |
| Components | `components_refresh`, `component_install`, `components_install_missing` |
| Clipboard | `clipboard_link`, `clipboard_dismiss` |
| Shell | `open_settings`, `open_link(kind)`, `set_badge(png)`, `app_update_check`, `app_update_install`, `quit` |

One event, `Update(Vec<Change>)`, carries everything from Rust to the UI:
`JobAdded`, `JobUpdated`, `JobRemoved`, `Progress`, `Order`, `Preview`, `PreviewRemoved`,
`PlaylistEntries`, `Settings`, `Components`, `System` (accent color, material support),
`Announce` (text for screen readers) and `Command` (a tray, shortcut or deep-link request
the UI must act on, such as focusing the URL field).

Deep links (`lovelydl://download?url=…&preset=…`) carry only a URL and an optional preset
name. They open a preview and never start a download or set yt-dlp options.

## Verification

Everything runs on the development PC (Windows 11):

1. Engine: unit tests, integration tests with `fake-ytdlp`, offline end-to-end runs through
   yt-dlp's generic extractor against a local HTTP server, and live smoke tests.
2. UI: Vitest, plus Playwright (Chromium, the engine WebView2 uses) screenshots and axe
   checks in mock mode, in light, dark and reduced motion.
3. Real app: built and launched here, driven through WebView2's remote-debugging port with
   Playwright, and its window captured from the screen so the real Mica/Acrylic material is
   in the picture.
